# 三个 SubAgent 的 Skill 部署方案

> 编制日期：2026-09-06 ｜ 配套文档：[能碳.md 第 8 节](../能碳.md#8-agent-架构主-agent--三个-subagent)

## 零、先分清 Tool 和 Skill

这是本方案的前提，混淆了后面全错。

| | **Tool（工具）** | **Skill（技能）** |
|---|---|---|
| 是什么 | 一个可调用的函数 | 一套方法论、判据、检查清单 |
| 回答 | **能做什么动作** | **怎么做才不出错** |
| 例子 | `align_emission_factors()` | 「跨库对齐时先比系统边界，边界不一致的因子不能直接比大小」 |
| 载体 | Python 函数 + `@beta_tool` | Markdown 指令文件 + 参考资料 + 校验脚本 |
| 已定义在 | [能碳.md §8.7](../能碳.md#87-工具集分配) | **本文档** |

> **同一个 tool，配不配 skill，产出质量差很远。**
> `align_emission_factors` 能把三个库的数拉出来；但**要不要提示边界不一致、分歧多大算异常、报告里怎么写**——那是 skill 的事。

## 一、三层结构

```
┌──────────────────────────────────────────────────────┐
│  L0 · 共用 Skill（三个 SubAgent 都装）                 │
│  碳核算口径公约 · 不确定性与置信度 · 证据接地           │
└──────────────────────────────────────────────────────┘
        ↓                  ↓                  ↓
┌───────────────┐  ┌───────────────┐  ┌───────────────┐
│ L1 · SubAgent1│  │ L1 · SubAgent2│  │ L1 · SubAgent3│
│ 负载基线      │  │ CFE 小时匹配 ⭐│  │ 跨库因子对齐  │
│ 任务画像      │  │ 电网碳强度    │  │ 因子库导航    │
│ 预测区间      │  │ 时序错配      │  │ 报告体例      │
│               │  │ 储能碳套利    │  │               │
└───────────────┘  └───────────────┘  └───────────────┘
```

**为什么分两层**：口径、不确定性表达、防幻觉这三件事，三个 SubAgent 都会犯同样的错。抽成共用层，改一处全生效；分散在各自 skill 里，迟早不一致。

## 二、L0 · 共用 Skill（3 个，必装）

### S0-1 `carbon-accounting-conventions` · 碳核算口径公约

**解决什么问题**：口径不一致是碳核算最高频的错误，且**错了看不出来**——数字照样能算出来，只是不可比。

**必须写进去的内容**：

| 条目 | 规则 |
|---|---|
| 单位统一 | 全流程 gCO₂e；隐含碳表用 kgCO₂e，**参与计算前必须 ×1000** |
| 双算法 | 地域法与市场法**必须同时输出**，不许只给一个 |
| 五字段标注 | `token_scope`、`include_embodied`、`embodied_method`、`energy_boundary`、`factor_version` 缺一不可 |
| 边界一致性 | 机型能效对比用 **IT 电耗**，不含 PUE；跨库因子比大小前先比系统边界 |
| 拒绝对比 | 口径不一致时**报错，不静默对比** |

**校验脚本**（skill 可带）：给一组结果，自动检查五字段是否齐全、单位是否一致。

> 📎 **依据**：[能碳.md §5.6 口径标注](../能碳.md#56-口径标注硬性要求)、[§B.5 单位一致性警示](../能碳.md#b5-碳足迹与生命周期问题三)

---

### S0-2 `uncertainty-and-confidence` · 不确定性与置信度表达

**解决什么问题**：LLM 天然倾向于给出确定语气的答案。碳核算里，**过度自信比答错更危险**——错了还能被发现，自信地错会被直接采信。

**必须写进去的内容**：

1. **结构化置信输出**：每条结论强制带 `confidence` 与 `sources` 字段（不是自由文本里提一句）
2. **置信度分级**：高（有直接数据支撑）/ 中（有间接或近似）/ 低（样本不足或方法外推）
3. **弃答机制**：数据不足以支撑结论时**主动说"答不了"并指出缺什么**，而不是降低标准硬答
4. **区间优先于点估计**：预测类结论必须给区间；只给单一数字会被误读为确定值
5. **近似必标**：用近似方法（如风光占比推算碳强度）时，结果上标"近似值"

> 📎 **文献依据**：检索显示，2025–2026 年防幻觉的有效做法包括**置信度感知的弃答机制**（confidence-aware abstention）、**结构化输出中强制 confidence 与 sources 字段**、以及**自一致性/采样分歧**作为可靠性信号。
> ProcessCarbonAgent（*Journal of Manufacturing Systems* 2024, 76: 429–442）采用**邻域检索 + 两阶段置信度评估**来提升根因分析的可信度——这与本 skill 的设计同源。

---

### S0-3 `evidence-grounding` · 证据接地

**解决什么问题**：Agent 编数字、编因子、编出处。这是碳核算场景的**头号风险**。

**必须写进去的内容**：

1. **只答检索到的**：所有数值必须来自工具返回或检索结果，**不许从模型记忆里生成因子值**
2. **逐条溯源**：每个关键数字附来源（哪张表、哪个库、哪个版本）
3. **反幻觉自检**：输出前逐条比对，声称的每个数值能否在检索片段中找到原文支撑
4. **检索不到就说没有**：不许用"相近项"凑数
5. **责任归属声明**：报告中明确「AI 生成内容需使用者复核，责任由使用者承担」

> 📎 **文献依据**：Preuss, Alshehri & You（*Journal of Cleaner Production* 2024, 466: 142824）讨论 LLM 用于 LCA 的幻觉风险与**责任归属**问题，明确结论是**从业者必须复核并对基于生成内容的决策负责**。
> LLMs-RAG-CFA 方法（arXiv 2408.09713，**注：检索显示仅有预印本**）在五个行业上验证了 RAG 可显著降低碳足迹核算偏差。
> 检索还显示，有效做法包括**逐句引用链接回原文页面**的引用模块。

## 三、L1 · SubAgent 1（能碳预测）专属 Skill

### S1-1 `workload-energy-baseline` · 负载能效基线构建 【必装】

**为什么需要**：预测的全部质量取决于基线。基线建错，后面全错。

**必须写进去的内容**：

| 条目 | 规则与理由 |
|---|---|
| 用中位数不用均值 | 算力任务功率分布**长尾严重**，均值会被少数极端任务拉偏 |
| 分组粒度 | 按「任务类型 × 机型」分组，**不要跨机型合并**（异构差异是本项目的核心假设） |
| 样本量门槛 | 默认 10；低于门槛标注「样本不足，不可靠」而非拒绝输出 |
| 离群处理 | 超出 均值±2σ 标记但**不自动剔除**——离群点可能正是要找的问题 |
| 基线失效信号 | 新机型、新任务类型、软件栈大版本变更 → 基线不适用，必须提示 |
| 只用 IT 电耗 | 基线不含 PUE，避免机房属性污染机型对比 |

---

### S1-2 `compute-task-profiling` · 算力任务画像 【必装】

**为什么需要**：训练、微调、推理的功率特征完全不同，混在一起预测必然失准。

**必须写进去的内容**：

- 四类任务的功率特征差异（训练：长时高位；推理：短时波动；微调：中等；数据处理：IO 密集低功率）
- **推理任务的 Token 口径**：`tokens_in + tokens_out` vs `tokens_out`，两者不可混算
- **训练任务不产出推理 Token**，改用训练消耗 Token 数，**与推理分开统计**
- 可延迟性的**判断依据**（不是判断本身——判断归人）：批量 vs 在线、有无 SLA、能否中断续跑
- 空置识别：装机但未被任务占用 ≠ 利用率低

> 📎 **依据**：[能碳.md §2.2 空置与使用强度](../能碳.md#22-空置与使用强度问题一问题三)、[§3.4 差异性分析](../能碳.md#34-差异性--为什么这批任务比那批费电)

---

### S1-3 `forecast-interval-construction` · 预测区间构造 【必装】

**必须写进去的内容**：

```
区间下界 = Σ [ 预计卡时 × 历史同类组合能耗的 P25 ]
区间上界 = Σ [ 预计卡时 × 历史同类组合能耗的 P75 ]
```

- **为什么用分位数而非正态假设**：能耗分布右偏，正态假设会低估上界
- 区间宽度本身是信息：**宽区间说明历史波动大或样本少，不是缺陷**
- 禁止黑箱模型：基线外推可解释可复现，不引入需训练的预测器
- **预测必须回测**：结果存 `forecast_records`，事后回填实测算偏差，用于下期校准

> 📎 **依据**：[能碳.md §8.3](../能碳.md#83-subagent-1--任务需求与能碳预测)、表 8 `forecast_records`

## 四、L1 · SubAgent 2（低碳识别）专属 Skill

### S2-1 `cfe-hourly-matching` · 24/7 无碳电力小时级匹配 【⭐ 最高优先级，强烈建议新增】

> **这是本方案最重要的一条建议。**

**为什么需要**：你的 SubAgent 2 要做的事，**业界已有标准方法论**——**24/7 Carbon-Free Energy（CFE）小时级匹配**与 Google 提出的 **CFE Score**。采纳它可以让你的指标从"自定义"变成"可对标、可引用"。

**核心内容**：

| 条目 | 规则 |
|---|---|
| **CFE Score 定义** | 衡量**每一小时**用电中被无碳电力匹配的比例 |
| **计入范围** | 既包括自签 PPA/自建绿电，**也包括电网整体电源结构中的无碳部分** |
| **弃电不计入** | **未被使用的 CFE 不贡献分数**——发出来没用上等于没有 |
| **未匹配负荷线性扣分** | 缺口按线性惩罚，不做非线性加权 |
| **时间分辨率** | **推荐小时级**；更长周期的分数由小时结果做**电量加权平均**得出 |
| **年度 vs 小时的落差** ⭐ | 年度账面可以 100% 绿电，小时级实际可能远低于此。**这个落差正是"时间错配"的量化表达** |

**对你的直接价值**：

1. **验证了你的架构判断**——「计入电网整体电源结构中的无碳部分」正是 `renewable_records.scope_level = grid` 存在的理由
2. **给你一个可对标的顶层指标**——CFE Score 与「每百万 Token 碳足迹」并列，一个衡量*电从哪来*，一个衡量*产出多少碳*
3. **论文层面**：年度匹配 vs 小时匹配的落差是一个成熟且有争议度的切入点，比自定义指标更容易被审稿人接受

> ⚠️ **务必自行核对官方定义**：CFE Score 的精确计算规则以 Google / 相关行业组织的官方方法学文件为准。本 skill 应引用原始方法学，**不要凭本文档的转述实现**。

---

### S2-2 `grid-carbon-intensity` · 电网碳强度获取与近似 【必装】

**必须写进去的内容**：

1. **优先级**：电网发布的分时碳强度 > 区域电网年度因子 > 由风光占比近似推算
2. **近似方法的适用条件与误差**：用 `grid_share_pct` 推算时，须说明假设（无碳电源的边际替代关系），**结果标"近似值"**
3. **区域差异**：不同区域电网因子差异大，**不许用全国平均值代替区域值**而不标注
4. **边际 vs 平均碳强度**：负载迁移决策理论上应看**边际**碳强度，但数据通常只有平均值——**这个局限必须写进报告**

---

### S2-3 `temporal-mismatch-analysis` · 时序错配分析 【必装】

**必须写进去的内容**：

- 相位差算法：两条归一化曲线做互相关，取相关系数最大处的滞后量
- 需要成对分析的曲线：负载 vs 光伏 / 负载 vs 风电 / 负载 vs 碳强度 / 负载 vs 电价 / IT 负载 vs 制冷
- **相关不等于因果**：相位差是描述性统计，不是机理结论
- 低碳窗口判据（双条件）与阈值可调要求
- **理论可迁移量 ≠ 实际可迁移量**：平台只算前者

> 📎 **依据**：[能碳.md §3.5 时序性](../能碳.md#35-时序性--什么时候费电绿电来的时候我在用吗)、[§8.4](../能碳.md#84-subagent-2--风光趋势匹配与低碳识别)

---

### S2-4 `storage-carbon-arbitrage` · 储能碳套利判据 【必装】

**为什么单独成一个 skill**：这是整个项目**最容易被想当然做错**的地方。

**核心判据**：

```
储能净减碳 = E_out × ( EF_放电时段 − EF_充电时段 ÷ η )

  > 0 → 真减碳    < 0 → 在增碳 ⚠️
  特例：充的是本会被弃掉的绿电 → EF_充电 取 0，全额为正
```

**必须写进去的内容**：

- **不假设储能一定减碳**——默认立场是"待验证"，不是"有效"
- `charge_source` 字段是该测算成立的**前提**，缺失时明确说"算不了"
- 结果为负时**必须标红并说明原因**，不许显示为 0 或隐藏
- 往返效率 η 应按实测填写，默认 0.90 仅为占位

## 五、L1 · SubAgent 3（因子对齐与核算）专属 Skill

### S3-1 `emission-factor-alignment` · 跨库因子对齐 【必装，核心】

**必须写进去的内容**：

1. **对齐前先比六项**：系统边界、地域范围、数据年份、单位、活动定义、上游假设
2. **边界不一致的因子不能直接比大小**（摇篮到大门 vs 摇篮到坟墓）
3. **匹配分级**：🟢 精确 / 🟡 近似（须标差异项）/ 🔴 无匹配（须人工填，**不许用相近项凑**）
4. **分歧呈现格式**：各库取值并列 + 分歧幅度（max ÷ min）
5. **绝不自动选定后隐藏分歧** —— 这是可审计性的底线
6. **选择建议要给理由**：地域匹配度、年份新旧、边界一致性、合规要求

> 📎 **文献依据**：*Environmental Science & Technology* 有两篇直接相关工作——
> 「Mitigating Grand Challenges in Life Cycle Inventory Modeling through the Applications of Large Language Models」（DOI 10.1021/acs.est.4c07634）
> 与「A Large Language Model-based Framework to Retrieve Life Cycle Inventory and Environmental Impact Data from Scientific Literature」（DOI 10.1021/acs.est.5c05955）。

---

### S3-2 `lca-database-navigation` · 因子库导航 【必装】

**必须写进去的内容**：各主流库的特点、适用场景与已知坑。

| 库 | 特点 | 适用 | 坑 |
|---|---|---|---|
| 中国生命周期基础数据库（CLCD 类） | 本土化程度高 | 国内产品碳足迹 | 覆盖面有限，更新周期长 |
| ecoinvent | 覆盖最广 | 国际对标、出口合规 | 欧洲视角，中国数据多为近似 |
| IPCC 缺省值 | 权威 | 缺乏本地数据时兜底 | 全球平均，粗 |
| 主管部门电网基准线因子 | 政策合规首选 | 履约核算、政府报送 | 发布有滞后 |
| 企业自建库 | 最贴合实际 | 内部管理与改进 | 不可对外比较 |

**查询方法**：可采用 Text2SQL（Few-shot CoT + Chain of Code）做 LCI 数据库的自然语言检索。

> 📎 **文献依据**：Zhang X., Guo X., Zhao J., Xiong J., Tian Y.，「Intelligent application of large language model to life cycle assessment methodology」，*Journal of Cleaner Production* 2025, 529: 146776（DOI 10.1016/j.jclepro.2025.146776）——该工作即采用 Text2SQL 结合 Few-shot CoT 与 Chain of Code 实现 LCI 数据库的自然语言查询。

---

### S3-3 `carbon-report-conventions` · 碳核算报告体例 【必装】

**报告必含七项**：

1. 结果（含[五字段口径标注](../能碳.md#56-口径标注硬性要求)）
2. 边界与假设（时间、空间、Scope 范围、排除项）
3. 活动数据来源与质量
4. **因子溯源**：用了哪个库、哪版、为什么选它
5. **不确定性**：跨库敏感性、数据缺口、近似方法
6. 局限声明
7. **责任声明**：AI 生成内容需复核，责任在使用者

**禁止事项**：不出具认证级结论、不声称符合 ISO 14064/14067、不隐藏分歧、不用相近因子凑数。

## 五-bis、分配问题相关的三个追加 Skill ⭐

[对标审计](./成熟工作流对标审计.md) 指出的分配规则缺失，需要追加三个 Skill：

| Skill | 装在 | 解决什么 | Skill 能解决的比例 |
|---|---|---|---|
| `allocation-hierarchy` | SubAgent 1 | 整机功耗分到任务 | 仅 ~20%，**瓶颈在硬件测量** |
| `shared-infra-allocation` | SubAgent 1/2 | 共享网络存储制冷分摊 | ~40% |
| **`boundary-and-amortization`** ⭐ | SubAgent 3 | **训练碳摊到推理 Token** | **~65%，最适合用 Skill 解决** |

📎 **完整可行性分析见 [分配问题的Skill可行性分析.md](./分配问题的Skill可行性分析.md)**

> ⚠️ **重要提醒**：不要以为装上 Skill 这三个问题就解决了。
> 第一个问题的瓶颈在**硬件测量能力**——Skill 只能让 Agent 诚实承认测不准，**不能让它变准**。

## 六、优先级与实施顺序

| 优先级 | Skill | 理由 |
|---|---|---|
| 🔴 **P0** | S0-1 口径公约、S0-3 证据接地 | 不装这两个，其余全部结论不可信 |
| 🔴 **P0** | S3-1 跨库因子对齐 | SubAgent 3 的存在意义就是它 |
| 🔴 **P0** | S2-4 储能碳套利 | 最容易做错、错了方向性错误 |
| 🟠 **P1** | S2-1 CFE 小时匹配 ⭐ | 把自定义指标升级为可对标方法论 |
| 🟠 **P1** | S0-2 不确定性与置信度、S1-1 负载基线 | 预测可信度的地基 |
| 🟡 **P2** | S1-2 任务画像、S1-3 预测区间、S2-2 电网碳强度、S2-3 时序错配 | 各自 SubAgent 的方法细节 |
| 🟡 **P2** | S3-2 因子库导航、S3-3 报告体例 | 可随实际使用逐步补全 |

**实施建议**：**先做 L0 三个共用 skill**。它们是所有 SubAgent 的共同地基，且不依赖任何 SubAgent 的实现进度，现在就能写。

## 七、每个 Skill 的文件结构（模板）

建议统一为：

```
agent/skills/<skill-name>/
├── SKILL.md          # 主指令：什么时候用、怎么做、硬性禁止事项
├── references/       # 参考资料（因子库特点、方法学摘要、公式推导）
└── scripts/          # 可选：校验脚本（如口径完整性检查、单位一致性检查）
```

`SKILL.md` 内容骨架：

```markdown
# <Skill 名称>

## 何时使用
（触发条件，写具体，别写"处理相关任务时"）

## 核心方法
（步骤、公式、判据）

## 硬性禁止
（绝对不能做的事，用祈使句）

## 常见错误
（这个领域里人和模型都容易犯的错）

## 输出要求
（格式、必含字段、标注要求）
```
