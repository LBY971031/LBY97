### 🔴 P0-1 · 分配规则（Allocation）完全缺失 —— 最严重

**问题**：`能碳.md` 全文没有处理**共享资源的能耗分配**。而这是算力碳足迹的**核心难题**，绕不过去。

**具体表现为三个未解问题**：

| 场景 | 现在怎么办 | 应该怎么办 |
|---|---|---|
| 一台 8 卡机同时跑 3 个任务，整机功耗怎么分到 3 个任务？ | **文档没说** | 按 ISO 分配层级 |
| 共享的网络、存储、制冷电耗怎么摊到各模型？ | **文档没说**（只笼统乘 PUE） | 需要明确分摊基准 |
| **一次训练产出的模型被后续百万次推理调用，训练的碳怎么摊到推理 Token 上？** | **文档完全没处理** | 这是共产品分配问题 |

> 🔴 **第三条尤其致命**。你的核心指标是「每百万 Token 碳足迹」。如果不处理训练碳的摊销，
> 那这个数字**只算了推理，漏掉了训练**——而训练往往是大头。
> 审稿人一定会问这个问题。

**成熟做法（ISO 分配优先级层级）**：

```
① 细分（subdivision）或系统扩展   ← 优先，能分开测就分开测
② 物理分配（physical allocation） ← 次之，按物理量分摊
③ 经济分配（economic allocation） ← 最后手段，按金额分摊
     并且全过程必须保持透明
```

**映射到算力场景**：

| 层级 | 算力场景的做法 | 可行性 |
|---|---|---|
| ① 细分 | **分卡计量**——`pynvml` 逐卡读功耗，直接归到占用该卡的任务 | ✅ 技术上可行，应作为首选 |
| ② 物理分配 | 按**卡时**、**显存占用**或**算力份额**分摊整机与共享设施能耗 | ✅ 退而求其次 |
| ③ 经济分配 | 按各任务计费金额分摊 | ⚠️ 仅在前两者都不可行时用 |

**训练碳摊到推理的规则（需你决策）**：
类比隐含碳摊销——训练碳按**模型预期总服务量**摊到每百万推理 Token。但"预期总服务量"是个估计值，
**必须作为显式假设写进口径标注**，且做敏感性分析。

**要改哪里**：
- [§5 模块三](../能碳.md#5-模块三--百万-token-碳足迹与服务器生命周期) 新增「分配规则」小节
- [§5.6 口径标注](../能碳.md#56-口径标注硬性要求) 增加两个字段：`allocation_method`、`training_amortization`
- 表 6 `carbon_records` 同步增加这两个字段

### 🔴 P0-2 · M&V 缺「调整项」，回测会得出错误结论

**问题**：文档 [§7.1](../能碳.md#71-工作流闭环) 的复核环节写的是「下周期**同口径**回测」。
但**同口径 ≠ 可比**。

**IPMVP 的基本节能量方程是**：

```
节能量 = 基线期能耗 − 报告期能耗 ± 常规调整 ± 非常规调整
                                    ↑ 文档里完全没有这一项
```

| 调整类型 | 针对什么 | 算力场景的例子 |
|---|---|---|
| **常规调整** | 预期会周期性变化的因素——**天气、产量** | **Token 产出量变了**、任务结构变了、季节性温度变化影响制冷 |
| **非常规调整** | 不预期变化的因素——设施规模与设计、设备运行方式、使用者类型 | 扩容加机柜、换机型、机房改造、业务线调整 |

**不做调整会怎样**（这是硬伤）：

> 假设你 7 月采纳了「长文本任务迁到机型 A」的措施，8 月能耗反而涨了 12%。
> 如果 8 月的 Token 产出量比 7 月涨了 30%，**措施其实是有效的**（单位产出能耗降了），
> 但不做产量调整，你会得出「措施无效」的错误结论并否决它。
>
> **反过来更危险**：业务萎缩时，什么都不做能耗也会降，会被误判为措施有效。

**要改哪里**：
- [§7.1 工作流闭环](../能碳.md#71-工作流闭环) 第 ⑦ 步：「同口径回测」→「**按 IPMVP 做常规与非常规调整后的规范化对比**」
- [§7.3 措施台账](../能碳.md#73-措施台账) 增加字段：`baseline_period`、`reporting_period`、`routine_adjustment`、`non_routine_adjustment`、`normalized_saving`
- 表 15 `measures` 同步

> 💡 **好消息**：你已经有「每百万 Token 碳足迹」这个**强度指标**，它天然做了产量归一化。
> 但**强度指标不能完全替代 IPMVP 调整**——任务结构变化、机型变化仍需非常规调整。

### 🔴 P0-3 · 工作流顺序错了：边界与口径应前置

**问题**：现在的七步是 `采集 → 分析 → 识别 → 测算 → 建议 → 执行 → 复核`。
**先采集，后定口径。** 而成熟的碳核算工作流一律是**先定边界与口径，再采数据**。

**为什么这是真问题**：
- 边界没定就采集 → 采到用不上的数据，或者**采漏了关键数据**（比如没意识到要分卡计量，事后补不回来）
- 口径没定就测算 → 算完发现口径不对，返工

**建议改为九步**：

```
① 定边界与口径   ← 新增前置。组织/运营边界、Scope 范围、功能单位、
                     分配规则、Token 口径、因子库选择
② 采集
③ QA/QC          ← 新增独立环节（见 P1-2）
④ 测算
⑤ 分析（三性）
⑥ 识别（高能耗/空置/低碳窗口）
⑦ 建议
⑧ 执行
⑨ M&V 验证       ← 原"复核"，按 IPMVP 规范化
```

**要改哪里**：[§7.1 工作流闭环](../能碳.md#71-工作流闭环) 整体重画

### 🟠 P1-1 · 功能单位未按 ISO 14067 规范定义

**问题**：文档说功能单位是「百万 Token」，但 ISO 14067 要求功能单位**清晰定义、可测量、与目标范围一致**。
标准里的经典示例是：不是「一盒洗涤剂」，而是「**洗 100 次衣服**」——即必须包含**功能、量、质量、时长**四要素。

「百万 Token」只有"量"，缺"功能"和"质量"。

**问题在哪**：100 万个短文本推理 Token 和 100 万个长文本推理 Token，**不是同一个功能**；
不同模型（7B vs 70B）产出的 100 万 Token，**质量也不同**。直接比大小会误导。

**建议的规范表述**：

> **功能单位**：由 <模型规格> 在 <服务质量约束，如 P95 首 Token 延迟 ≤ X ms> 下，
> 完成 100 万 Token 的 <任务类型：短文本推理 / 长文本推理 / 批量推理> 输出。

**要改哪里**：[§1.4 核心指标体系](../能碳.md#14-核心指标体系)、[§5.6 口径标注](../能碳.md#56-口径标注硬性要求)

> ⚠️ 这条对**论文**尤其重要。审稿人若熟悉 ISO 14067，功能单位定义不规范是第一个会被挑的点。

### 🟠 P1-2 · 缺 QA/QC 独立环节与数据质量评级

**问题**：文档只有「待确认预览区」这一道人工关卡，**没有系统的数据质量评价**。

**成熟做法**：优先收集一手数据并记录来源、评估数据质量、记录计算方法、定期审计、必要时独立第三方评审。

**建议新增**：

| 数据质量维度 | 分级示例 |
|---|---|
| **来源** | 一手实测 / 二手台账 / 文献估算 / 缺省值 |
| **时间代表性** | 同期 / 一年内 / 更旧 |
| **地域代表性** | 本园区 / 同区域 / 全国 / 全球 |
| **技术代表性** | 同机型 / 同类机型 / 泛化 |
| **完整性** | 全量 / 抽样 / 部分缺失 |

每条活动数据打一个综合质量分，**汇总到结果的不确定性评估里**。

**要改哪里**：[§3.2 统一接入流程](../能碳.md#32-统一接入流程) 增加质量评级步骤；表 1–5 增加 `data_quality` 字段

### 🟠 P1-3 · 缺不确定性评估（ISO 强制要求）

**问题**：ISO 14067 要求可信研究**至少要有定性的不确定性评估**。
文档现在只有 SubAgent 1 的预测区间和 SubAgent 3 的跨库敏感性，**没有对最终碳足迹结果做统一的不确定性表述**。

**建议**：最终结果必须附一段不确定性说明，涵盖：
活动数据质量、因子选择分歧、分配规则假设、训练碳摊销假设、近似方法（如碳强度推算）。

**要改哪里**：[§5.6](../能碳.md#56-口径标注硬性要求) 之后新增「不确定性评估」小节

### 🟡 P2-1 · Agent 层缺 Eval

**问题**：文档 [§16.8](../能碳.md#168-测试要求) 只有单元测试（测 `core/` 的算法），
**没有 Agent 层的评测**。Agent 说错话怎么发现？现在没有机制。

**成熟做法**：eval-driven —— 先建评测集，再迭代 prompt 和 skill。

**建议建三类评测集**：

| 类型 | 内容 | 判据 |
|---|---|---|
| **事实性** | 给定数据，Agent 报的数字是否与确定性计算一致 | 完全一致，否则失败 |
| **边界遵守** | Agent 是否拒答了数据不足的问题、是否标注了近似值 | 是/否 |
| **分歧呈现** | 跨库因子不同时，是否呈现了分歧而非自动选一个 | 是/否 |

**要改哪里**：[§16.8](../能碳.md#168-测试要求) 增加 Agent eval 要求；新增 `evals/` 目录
