# 工作流搭建方案

> 编制日期：2026-09-07
> 两条新增约束：
> ① SubAgent 1 的任务监测须**按服务器机型分别核算空置率**
> ② **数据有就是有、没有就是没有，存在性判定不交给 LLM**
>
> 本文把这两条落成可执行的工作流。

---

## 零、先把第二条约束形式化

「不能交给 LLM，否则会瞎编」——这句话不能只写在提示词里，**必须变成代码层强制**。

### 问题的根源：二态不够用

| 传统做法 | 模型看到什么 | 后果 |
|---|---|---|
| 有值 → 数字；没值 → `null` / 空 / `0` | 一个空位 | **模型会去填它**——用相邻时段、相似机型、平均值，甚至凭空编 |

最危险的一种：**把"没测到"当成 `0`**。
> 「7 月 3 日 14:00 该机型能耗 0 kWh」——到底是**真的没耗电**，还是**采集器那小时挂了**？
> 二态表示法里这两者长得一模一样。**结论会完全相反。**

### 解法：四态数据 + 显式缺失清单

每个数据点必须带**来源状态**：

| 状态 | 含义 | 谁能产生 | Agent 能怎么用 |
|---|---|---|---|
| `measured` | **实测值** | 采集器 / 文件导入 | 直接用 |
| `derived` | 由实测值**确定性推导** | `core/` 算法 | 直接用，但须能追溯到源 |
| `imputed` | **补全值** | **仅 `core/`，且必须记方法** | 用之前必须声明补全方法 |
| `absent` | **没有。不是 0，不是 null，是"没有"** | 采集器/导入器判定 | **只能转述"无数据"，禁止推断** |

> 🔴 **`absent` 与 `0` 必须在数据库层就分开存。**
> 建议：数值字段可空，另设 `value_status` 字段。`absent` 时数值字段为 NULL 且 `value_status='absent'`；
> 真实测得 0 时数值为 0 且 `value_status='measured'`。

---

### 工具返回契约（硬性）

所有 SubAgent 工具的返回值必须是统一信封，**不许直接返回裸数据**：

```json
{
  "status": "ok | partial | no_data",
  "data": { ... },
  "coverage": {
    "expected_points": 720,
    "actual_points": 512,
    "pct": 71.1
  },
  "absent_ranges": [
    {"from": "2026-07-03T14:00", "to": "2026-07-03T18:00", "reason": "采集器离线"},
    {"scope": "server_model=H100-8卡", "reason": "该机型未接入采集"}
  ],
  "imputed_fields": [
    {"field": "pue", "method": "月度均值填充", "count": 12}
  ],
  "quality_grade": "A | B | C | D"
}
```

**关键设计**：`absent_ranges` 是**显式列出来的**，不是让模型从数据里自己发现哪里缺了。
模型不需要"注意到"缺失——**缺失被直接告知**。

---

### 代码层的三道强制闸（比提示词可靠）

| 闸 | 位置 | 做什么 |
|---|---|---|
| **闸一：不给 null** | `core/` 各查询函数 | 缺失时**不返回 `null` 占位**，而是把该时间点整个从 `data` 里剔除，同时登记进 `absent_ranges`。**模型看不到空位，就没有空位可填** |
| **闸二：自动附加禁令** | `agent/boundary.py` | 出网前检测到 `absent_ranges` 非空，**自动追加固定文本**：「以下范围无数据，不得推断、不得用相邻时段或相似机型替代」 |
| **闸三：结论回检** | `agent/verifier.py`（新增） | Agent 输出后，逐个数字**回查是否在工具返回的 `data` 中存在**。查不到的数字 → 标记为疑似编造并拦截 |

> **闸三是最后一道保险。** 前两道靠"不给机会"，第三道靠"事后核对"。
> 这与 [能碳.md §8.2](../能碳.md#82-主-agent编排层) 的原则一致：**数字由代码算，话由 Agent 说**——
> 那么 Agent 说出的每个数字，都应该能在代码算出的结果里找到。

---

### Agent 侧的硬性规则

| 收到 | 必须怎么做 | 禁止 |
|---|---|---|
| `status: no_data` | 只说「该范围无数据」+ 指出缺什么 | 推断任何数值 |
| `status: partial` | **结论中必须声明覆盖率**（如「基于 71% 覆盖率的数据」） | 当作完整数据下结论 |
| `imputed_fields` 非空 | **必须转述补全方法** | 把补全值当实测值 |
| `quality_grade: C/D` | 必须标注「数据质量偏低，结论仅供参考」 | 给出高置信度表述 |

**四条绝对禁止**：

1. ❌ 用相邻时段的值代替缺失时段
2. ❌ 用相似机型的值代替未接入机型
3. ❌ 用均值/中位数填补后当实测值用
4. ❌ **把 `absent` 当 `0` 参与求和** ← 最隐蔽、最致命

## 一、整体工作流（九步详解）

### 总览

```
① 定边界与口径 ─→ ② 采集 ─→ ③ QA/QC ─→ ④ 测算 ─→ ⑤ 分析 ─→ ⑥ 识别
                                                                    │
   ┄┄┄┄┄┄┄┄┄┄ 到这里为止，一行 LLM 代码都没有 ┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┤
                                                                    ↓
                              ⑨ M&V 验证 ←─ ⑧ 执行 ←─ ⑦ 归因与建议
                                    │
                                    └──→ 回到 ①，下一周期
```

**三条贯穿全流程的规则**：

| 规则 | 含义 |
|---|---|
| **口径先行** | ① 未完成，② 之后全部拒绝执行 |
| **LLM 在 ⑥ 之后才介入** | ④⑤⑥ 的数字在 Agent 看到之前已全部算完落库 |
| **每步有完成判据** | 判据不满足不进入下一步，避免"看起来做完了" |

---

### ① 定边界与口径

| 项 | 内容 |
|---|---|
| **目的** | 把所有影响结果**可比性**的选择一次性固化并锁版本 |
| **谁执行** | **人**（你），平台提供配置界面 |
| **输入** | 无（这是起点） |
| **输出** | **口径配置快照**（一条带版本号的记录） |

**必须定的十一项**：

| # | 项目 | 可选值 / 说明 |
|---|---|---|
| 1 | 组织边界 | 哪些服务区、哪些机房纳入 |
| 2 | 运营边界 | Scope 1/2/3 各含什么、排除项及理由 |
| 3 | 时间边界 | 统计周期 + **时段粒度**（建议与碳强度发布粒度对齐，通常 1 小时） |
| 4 | **功能单位** | 按 ISO 14067 写全：`<模型规格> 在 <QoS约束> 下完成 100 万 Token 的 <任务类型> 输出` |
| 5 | **Token 口径** | A 简单相加 / B 仅输出 / C 阶段加权（**建议 A 与 C 都出**） |
| 6 | 分配层级偏好 | 优先尝试哪一级（细分 → 物理 → 经济） |
| 7 | **Boundary** | B（不含训练碳）/ C（含）。**建议两版都出** |
| 8 | 隐含碳摊销 | 等效运行小时 / 日历时长 |
| 9 | 电耗边界 | 仅 IT / 含 PUE |
| 10 | 因子库 | 选定一个，或启用多库对齐 |
| 11 | 阈值集 | 高能耗系数、最短时长、样本量门槛、残差告警线、寿命分档系数、消纳率分级线 |

**完成判据**：
- ✅ 十一项全部有值（不许留空走默认）
- ✅ 快照已锁定并生成版本号
- ✅ 后续所有结果记录都能绑定到这个版本号

**常见错误**：
- ❌ 跳过这步直接采集 → 采漏关键数据，事后补不回来
- ❌ 中途改口径但不重新锁快照 → 前后结果混在一起，无法追溯

**产出落到**：`caliber_snapshot` 表（**需新增**）

---

### ② 采集

| 项 | 内容 |
|---|---|
| **目的** | 把五类数据接进来，**且如实标记有无** |
| **谁执行** | 平台采集器 + 人（文件上传） |
| **输入** | ① 的口径快照（决定采什么粒度） |
| **输出** | 五类活动数据表 |

**五类数据的接入方式**：

| 类 | 数据 | 途径 | 关键点 |
|---|---|---|---|
| A | 能耗 | 文件导入 / GPU / IPMI / 电表 | **逐卡与整机必须都采**——整机用于校准逐卡 |
| B | Token 计量 | 推理服务日志 / 网关 | 须带 `model_id`；若采集器支持，分 prefill/decode 阶段 |
| C | 风光储 | 园区自采 + 电网发布 | **`scope_level` 必填**，园区与电网不可混 |
| D | 任务与机型 | 调度系统导出 + 台账 | `cards_used` 必填（空置率分子）；`idle_power_w_per_card` 必填 |
| E | 设备生命周期 | 资产台账 | `cumulative_equiv_hours` 需持续累加 |

**硬性要求**：
- 每条数据打 `value_status`（measured / derived / imputed / absent）
- **缺失登记为 `absent`，不填 0、不填 null**
- 实时采集按批次确认，不逐条

**完成判据**：
- ✅ 覆盖率统计已生成（按 数据类型 × 时段 × 机型）
- ✅ 逐卡与整机功耗都已入库（若走路径 A/B）

**常见错误**：
- ❌ 只采逐卡不采整机 → 无法做回加校准
- ❌ 把缺失存成 0 → 后续全部结论污染

**产出落到**：`energy_records`、`token_records`、`renewable_records`、`storage_records`、`job_records`、`device_lifecycle`

### ③ QA/QC

> **这一步的产出不是"干净的数据"，而是「哪些分析能做、哪些做不了」的清单。**
> 这是它必须独立成步的理由。

| 项 | 内容 |
|---|---|
| **目的** | 判定数据可用性边界 |
| **谁执行** | 平台自动 + **人确认** |
| **输入** | ② 的原始数据 |
| **输出** | **数据可用性清单** |

**五个动作**：

1. **覆盖率统计** —— 按 数据类型 × 时段 × 机型 × 模型 逐格算
2. **数据质量分级** —— 五维打分：
   | 维度 | 分级 |
   |---|---|
   | 来源 | 一手实测 / 二手台账 / 文献估算 / 缺省值 |
   | 时间代表性 | 同期 / 一年内 / 更旧 |
   | 地域代表性 | 本园区 / 同区域 / 全国 / 全球 |
   | 技术代表性 | 同机型 / 同类机型 / 泛化 |
   | 完整性 | 全量 / 抽样 / 部分缺失 |
3. **异常值标记** —— **只标记不删除**（离群点可能正是要找的问题）
4. **回加校验** —— `Σ_k E_IT(m,k,t) + 空载能耗(m,t) ≟ 整机实测(m,t)`，残差 > 5% 告警
5. **待确认预览区人工确认** —— 解析结果逐行可改，确认后才入库

**完成判据**：
- ✅ **数据可用性清单已生成**，明确列出：哪些 (机型 × 模型) 格子能算、哪些不能、缺什么
- ✅ 人工确认已完成
- ✅ 每条数据有 `quality_grade`

**常见错误**：
- ❌ 把 QA/QC 当采集的附属，不产出可用性清单 → 后面到 ⑦ 才发现算不出来
- ❌ 自动删除异常值 → 把要找的问题删掉了

**产出落到**：`data_availability` 表（**需新增**）+ 各表的 `quality_grade` 字段

---

### ④ 测算

| 项 | 内容 |
|---|---|
| **目的** | 算出**所有确定性数字** |
| **谁执行** | **纯 `core/`，零 LLM 参与** |
| **输入** | ③ 的可用性清单 + 已确认数据 |
| **输出** | 全部测算结果 |

**执行顺序（有依赖，不可乱序）**：

```
④.1 空载能耗（分机型）      ← 必须最先，因为 ④.2 要扣它
④.2 能耗分摊（三级路径 + 回加约束）
④.3 加 PUE
④.4 运营碳排（分时段算，双算法）
④.5 硬件隐含碳（按等效运行小时）
④.6 训练碳摊销（Boundary C 时；区分自训/外部）
④.7 Token 归集（A 口径 + C 加权口径）
④.8 矩阵计算 → gCO₂e/MTok
④.9 成本（分时电价 + 需量）
```

**完成判据**：
- ✅ **四道交叉校验全部通过**：能耗回加、碳排回加、口径一致性、量纲抽查
- ✅ 每条结果带完整口径标注（七字段）
- ✅ 算不出的格子标 `absent` 且有 `absent_reason`

**常见错误**：
- ❌ 先汇总能耗再乘平均碳强度
- ❌ 把空载能耗摊给模型
- ❌ 自训模型训练碳算两遍
- ❌ 隐含碳 kg/g 未换算

**产出落到**：`carbon_records`、结果矩阵

### ⑤ 分析

| 项 | 内容 |
|---|---|
| **目的** | 从数字里读出**结构**（差异、周期、波动） |
| **谁执行** | **纯 `core/`** |
| **输入** | ④ 的测算结果 |
| **输出** | 分析指标 |

**三块内容**：

| 块 | 产出 |
|---|---|
| **三性分析** | 差异性（模型×机型能效矩阵、CV、离群）｜时序性（周期分解、自相关、相位差）｜不稳定性（滚动波动、变点、尖峰） |
| **CFE 小时匹配** | 逐小时无碳电力匹配度；弃电不计入；未匹配负荷线性扣分 |
| **生命周期** | 使用强度、等效寿命消耗率、LCC、残值、可再利用潜力 |

**完成判据**：
- ✅ **所有分析参数已随结果存档**（窗口大小、阈值、权重）——不存参数的结果无法复现
- ✅ 样本量不足的组合已标注

**常见错误**：
- ❌ 参数写死在代码里不存档 → 换个窗口结果就变，但没人知道当时用的什么
- ❌ 机型对比用了含 PUE 的电耗 → 比的是机房好坏不是机型好坏

**产出落到**：`analysis_results`（含 `params` JSON）

### ⑥ 识别

| 项 | 内容 |
|---|---|
| **目的** | 出**候选清单**，供 ⑦ 归因 |
| **谁执行** | **纯 `core/`** |
| **输入** | ④⑤ 的结果 |
| **输出** | 五类候选清单 |

**五类清单**：

1. 高能耗时段（起止、超出幅度、分级、五维归因数据）
2. 长期空置设备（连续 N 天空置率超阈值）
3. **「高能效 × 高空置」反常组合** ⭐
4. 低碳窗口 / 弃电窗口 / 高碳窗口
5. 低效「模型 × 机型」组合

**完成判据**：
- ✅ 每条候选都能追溯到支撑它的原始数据（证据链接）
- ✅ 清单已按严重程度排序

**常见错误**：
- ❌ 在这一步下业务结论（「这是故障」）→ 平台只标记统计反常，判断归人

**产出落到**：候选清单表

### ⑦ 归因与建议

> **LLM 首次介入。到这一步为止，所有数字都已算完并落库。**

| 项 | 内容 |
|---|---|
| **目的** | 解释**为什么**，给出**措施建议** |
| **谁执行** | **主 Agent + 三个 SubAgent** |
| **输入** | ④⑤⑥ 的聚合结果（**只读**） |
| **输出** | 归因结论、措施建议、报告初稿 |

**执行链**：

```
主 Agent 分解问题
   ├─ SubAgent 1（预测）→ 未来任务的能碳预测
   ├─ SubAgent 2（低碳）→ CFE 匹配、低碳窗口、迁移建议    ← 依赖 SubAgent 1
   └─ SubAgent 3（核算）→ 因子对齐、碳足迹、报告          ← 独立，可先跑
主 Agent 汇总 + 冲突仲裁
```

**完成判据**：
- ✅ **结论回检通过**：Agent 输出的每个数字都能在工具返回中找到
- ✅ 数据缺失已在结论**开头**声明（不许放末尾小字）
- ✅ 所有 Agent 输出带 🤖 标注

**常见错误**：
- ❌ 让 Agent 算数字 → 违反「数字由代码算」
- ❌ Agent 填补 `absent` 格子
- ❌ 把时间相关说成因果

**产出落到**：`measures`（建议）、报告文件

### ⑧ 执行

| 项 | 内容 |
|---|---|
| **目的** | 把措施落地 |
| **谁执行** | **人**（你和运维） |
| **输入** | ⑦ 的措施建议 |
| **输出** | 措施状态更新 |

**动作**：措施评审 → 采纳/否决 → 执行 → **记录执行时间点**（M&V 要用）

**完成判据**：
- ✅ 每条措施状态明确（待评估/已采纳/已执行/已否决）
- ✅ 已执行的措施有准确的执行时间点

**常见错误**：
- ❌ 不记执行时间 → ⑨ 无法划分基线期与报告期

> ⚠️ **平台不自动执行任何调度或控制。** 见 [能碳.md §1.5](../能碳.md#15-它不解决什么问题先说清楚)。

---

### ⑨ M&V 验证

| 项 | 内容 |
|---|---|
| **目的** | 验证措施**真的有效**，而不是业务量变了 |
| **谁执行** | `core/` 计算 + **人**判断调整项 |
| **输入** | ⑧ 的执行时间点 + 前后两期数据 |
| **输出** | 规范化节能量，回填 `measures` |

**IPMVP 基本方程**：

```
节能量 = 基线期能耗 − 报告期能耗 ± 常规调整 ± 非常规调整
```

**两类调整项（不做就会得出错误结论）**：

| 类型 | 针对 | 算力场景的例子 |
|---|---|---|
| **常规调整** | 预期会周期性变的 | **Token 产出量变化**、任务结构变化、季节温度影响制冷 |
| **非常规调整** | 不预期变的 | 扩容加机柜、换机型、机房改造、业务线调整 |

**为什么必须做**：
> 7 月采纳措施，8 月能耗涨 12%。若 8 月 Token 产出涨 30%，**措施其实有效**（单位产出能耗降了）。
> 不做产量调整会否决一个好措施。**反过来更危险**：业务萎缩时什么都不做能耗也降，会被误判为有效。

**完成判据**：
- ✅ 基线期与报告期已明确定义
- ✅ **调整项已逐条列出并说明依据**
- ✅ **口径一致性检查通过**（口径不同则拒绝对比并报错）
- ✅ 实际收益已回填，与预期收益并列展示

**常见错误**：
- ❌ 只用「同口径」就直接比 → 同口径 ≠ 可比
- ❌ 用强度指标（每百万 Token 碳足迹）替代全部调整 → 它只归一化了产量，**任务结构和机型变化仍需非常规调整**

**产出落到**：`measures` 的 `baseline_period`、`reporting_period`、`routine_adjustment`、`non_routine_adjustment`、`normalized_saving` 字段

## 二、SubAgent 1 的监测流程（含分机型空置率）

### 2.1 为什么空置率必须按机型分开算

| 只看园区总空置率 | 分机型看 |
|---|---|
| 「园区空置率 32%」 | 「机型A 28%、机型B **81%**、机型C 8%」 |
| 看不出问题在哪 | **机型B 明显异常，值得查** |

**三个只有分机型才能发现的问题**：

1. **调度偏好失衡** —— 某机型长期没人用（驱动老、框架不兼容、排队策略问题）
2. **空载浪费不等价** —— 同样 30% 空置率，待机功率高的机型浪费的电多得多
3. **反常组合** ⭐ —— 结合[差异性分析](../能碳.md#34-差异性--为什么这批任务比那批费电)的能效矩阵，
   如果**能效最高的机型空置率也最高**，说明调度策略在浪费最好的资源。**这是最有价值的发现之一。**

### 2.2 计算式

```
【按机型】
  逻辑空置率(m,t) = ( 装机卡数(m) − 被占用卡数(m,t) ) ÷ 装机卡数(m)
  空置卡数(m,t)   = 装机卡数(m) − 被占用卡数(m,t)
  空载能耗(m,t)   = 空置卡数(m,t) × 单卡待机功率(m) × Δt
  空载电费(m,t)   = 空载能耗(m,t) × 该时段电价
  空载碳排(m,t)   = 空载能耗(m,t) × PUE × 该时段碳强度

【园区汇总】
  园区空载能耗(t) = Σ_m 空载能耗(m,t)
  空载能耗占比    = 园区空载能耗 ÷ IT电耗 × 100%

【物理空置（机房层面）】
  物理空置率 = ( 可容纳机位 − 已装机位 ) ÷ 可容纳机位
```

### 2.3 数据前提与缺失后果（体现"有就是有"）

| 缺什么 | 后果 | **绝不允许的做法** |
|---|---|---|
| 装机卡数(m) | **该机型空置率算不出** | ❌ 用其他机型的装机数估 |
| 被占用卡数(m,t) | **该机型该时段空置率算不出** | ❌ 用相邻时段的占用数代替 |
| 单卡待机功率(m) | 空置率能算，**空载能耗算不出** | ❌ 用额定功率的固定百分比估 |
| 分时电价 | 空载能耗能算，**空载电费算不出** | ❌ 用月均电价代替后当精确值 |
| 分时碳强度 | **空载碳排算不出**（或只能给近似并标注） | ❌ 不标注就用年均因子 |

> **注意最后一行**：分时碳强度拿不到时，可以用近似方法算，但**必须标注为近似值**——
> 这与「有就是有」不冲突：**近似是被允许的，隐瞒近似不被允许。**

### 2.4 SubAgent 1 的完整监测流程

```
【core/ 层 —— 确定性，无 LLM】

  ① 读园区结构表 → 各机型装机卡数
       ├─ 缺 → 该机型标记 absent，退出该机型的全部空置分析
       └─ 有 ↓
  ② 读任务记录 → 各机型各时段被占用卡数
       ├─ 缺 → 该时段标记 absent
       └─ 有 ↓
  ③ 算 逐机型空置率 + 空置卡数
       ↓
  ④ 读机型台账 → 单卡待机功率
       ├─ 缺 → 空载能耗标记 absent（空置率结果保留）
       └─ 有 ↓
  ⑤ 算 空载能耗 / 电费 / 碳排
       ↓
  ⑥ 与能效矩阵交叉 → 标记「高能效 × 高空置」反常组合
       ↓
  ⑦ 识别长期空置设备（连续 N 天空置率 > 阈值）
       ↓
  ⑧ 组装工具返回信封（含 coverage / absent_ranges / quality_grade）

  ┄┄┄┄┄┄┄┄┄ 数据边界 ┄┄┄┄┄┄┄┄┄

【SubAgent 1 层 —— LLM，只读上面的聚合结果】

  ⑨ 解读：哪个机型空置异常、浪费了多少、可能什么原因
  ⑩ 声明：哪些机型/时段无数据、覆盖率多少、哪些结论因此给不出
```

> **第 ⑧ 步和第 ⑨ 步之间是硬边界。** ⑧ 之前的每个数字都已经算完落库，
> ⑨ 只是在读一份已经写好的报表。

### 2.5 输出

- 📊 **分机型空置率矩阵**（机型 × 时段热力图）
- 💸 **分机型空载浪费对照表**：空置率 / 空载能耗 / 电费 / 碳排
- ⚠️ **「高能效 × 高空置」反常组合清单** ⭐
- 📋 长期空置设备清单
- 🚫 **无数据清单**：哪些机型/时段没有数据、缺的是哪一项

## 三、数据缺失时，各环节怎么退化

**核心原则：局部缺失不拖垮整体，但必须明说缺了什么。**

| 缺什么 | 谁受影响 | 退化后还能做什么 |
|---|---|---|
| 某机型未接入采集 | SubAgent 1 该机型分析 | **其余机型照常**，结论中列出未覆盖机型 |
| 某时段采集器离线 | 该时段全部分析 | 其余时段照常，**覆盖率随结论一起报出** |
| 待机功率未实测 | 空载能耗 | **空置率照常给**，空载能耗标 absent |
| 电网风光数据缺 | SubAgent 2 全部 | SubAgent 1、3 照常，主 Agent 说明低碳识别不可用 |
| Token 计量缺 | 每百万 Token 指标 | 退回按时段/任务口径，**明确标注口径已降级** |
| 多因子库只有一个 | SubAgent 3 跨库对齐 | 单库核算照常，**敏感性分析不可用** |

**主 Agent 汇总时的硬性要求**：
> 任何一个 SubAgent 返回 `no_data` 或 `partial`，主 Agent 的最终结论**开头就要说明**，
> 不许放在末尾的小字里，更不许省略。

## 三-bis、三个 SubAgent 的提示词该放一个文件还是三个？

### 结论：**分三个，但共用部分抽出来**

```
agent/prompts/
├── _shared.md              ← 共用层：口径公约 · 数据契约 · 四条禁令 · 输出格式
├── orchestrator.md         ← 主 Agent：分解 · 调度 · 汇总 · 冲突仲裁
├── sub1_forecast.md        ← SubAgent 1：任务需求与能碳预测
├── sub2_lowcarbon.md       ← SubAgent 2：风光趋势匹配与低碳识别
└── sub3_factor.md          ← SubAgent 3：因子对齐与碳核算报告

运行时加载：某 SubAgent 的系统提示词 = _shared.md + 自己那份.md（拼接）
```

### 五条理由

| # | 理由 | 说明 |
|---|---|---|
| 1 | **运行时形态决定文件形态** ⭐ | 你已定「每个 SubAgent 是一次**独立的 Tool Runner 会话**」（[能碳.md §8.9](../能碳.md#89-技术实现要点)）。既然运行时是三个独立会话，各自加载各自的提示词最直接；**合成一个文件，到运行时还得切开，多此一举且易错** |
| 2 | **改一个不影响另一个** | 合并文件里改 SubAgent 1 的措辞，有可能误伤 2 和 3。分开后改动半径可控 |
| 3 | **上下文经济** | 每个会话只加载自己需要的内容。SubAgent 1 不需要知道跨库因子对齐的规则，加载了就是浪费 token 且分散注意力 |
| 4 | **与工具集分开挂载的架构一致** | 工具已在代码层按 Agent 分开挂载。提示词合并会造成**认知错位**——文件说"你们三个"，运行时却各拿各的工具 |
| 5 | **便于单独做 eval** | 三类评测集（事实性 / 边界遵守 / 分歧呈现）需要分别针对各 SubAgent 跑，文件分开才好挂钩 |

### 共用部分抽出来解决什么

**合并派最强的论据是「避免三份拷贝不一致」**——这个担心是对的，但**解法是抽取而不是合并**。

`_shared.md` 应该放：

| 内容 | 为什么共用 |
|---|---|
| 碳核算口径公约 | 三个 Agent 都要遵守同一套单位和标注规则 |
| **数据存在性契约** | 四态数据、`absent` 处理、四条绝对禁止——三个都必须遵守 |
| 「数字由代码算，话由 Agent 说」 | 底线原则 |
| 输出格式规范 | 结构化字段、置信度、来源标注 |
| 脱敏与数据边界 | 三个共用同一出口 |

各自的 `.md` 只放**该 Agent 独有的**：职责、可用工具清单、领域方法论、输出结构、该 Agent 特有的禁令。

### 什么情况下反而该合并

诚实起见，说清楚**例外**：

> 如果你后来把架构改成「**一个会话内的三个模式**」（同一个 Agent 靠提示词切换角色，共用一套工具），
> 那就该合并成一个文件——因为运行时本来就是一份上下文。
>
> **但那样会失去工具隔离**，越界从"不可能"退化成"不应该"。按现有架构不建议。

### 建议的文件骨架

每个 `sub*.md` 用同一套结构，便于对照和维护：

```markdown
# SubAgent N · <名称>

## 你的职责
（一句话 + 三到五条具体职责）

## 你的时态
（面向未来 / 面向过去 —— 这决定你能说什么）

## 可用工具
（清单 + 每个工具返回什么）

## 领域方法论
（该 Agent 特有的判据、公式适用条件、常见陷阱）

## 输出结构
（必含字段、格式模板）

## 本 Agent 特有的禁令
（除 _shared.md 的通用禁令外，额外的）

## 数据缺失时的行为
（缺哪类数据 → 哪些结论给不出）
```

### 与 Skill 文件的关系

**提示词（prompt）与技能（skill）是两层，不要混在一起**：

| | 提示词 `agent/prompts/` | 技能 `agent/skills/` |
|---|---|---|
| 是什么 | **这个 Agent 是谁、能干什么** | **某类任务怎么做才对** |
| 何时加载 | 会话开始时**全量加载** | 任务匹配时**按需加载** |
| 例子 | 「你是 SubAgent 3，负责因子对齐」 | 「跨库对齐时先比系统边界」 |
| 变更频率 | 低 | 高（随方法论演进） |

> 提示词里应该**引用** skill，而不是把 skill 内容抄进去。
> 抄进去会导致两处不一致，且提示词越来越臃肿。
