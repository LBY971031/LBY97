# 一、地基：`agent/contract.py`（71 行）

**整套设计的第一块砖。** 它不 import 任何本项目模块——被所有人依赖，不依赖任何人。

| 代码 | 含义 |
|---|---|
| `class ValueStatus` | 四态：`measured` 实测 / `derived` 推导 / `imputed` 补全 / **`absent` 没有** |
| `class ToolStatus` | 工具整体状态：`ok` / `partial` / `no_data` |
| `class AbsentRange` | 一段明确的缺失：原因、起止、范围 |
| `class ToolEnvelope` | **所有工具的统一返回结构**，禁止返回裸数据 |
| `drop_absent()` | 把 absent 的点**从数据里剔除**，单列成缺口声明 |
| `safe_sum()` | 遇到一个 absent 就返回 `None` |

### 为什么是四态而不是「有值/null」

`null` 有歧义：它可能是"没测到"，也可能是"测得是 0"。这两件事在碳核算里天差地别——前者该写"无法计算"，后者是真实的零。二态表达迟早把前者退化成后者。

### `drop_absent()` 的关键在「剔除」而非「标记」

```python
kept, gaps = drop_absent(points)   # 缺失的点不在 kept 里
```

如果留 `None` 占位，模型看见空位就会想填。**看不到空位，就没有空位可填。** 缺口另外单列，模型知道"这里缺了"，但拿不到一个可以覆盖的槽位。

### `safe_sum()` 是「有就是有，没有就是没有」唯一的代码兑现

```python
def safe_sum(points, key):
    for p in points:
        if p.get("value_status") == "absent":
            return None          # ← 不是跳过，不是当 0，是整个求和作废
```

样本里 srv-03 缺 15 分钟数据，所以全站能耗返回 `null` 而不是三台之和 8.0912——**把三台当全站就是少算**。

| 函数 | 含义 |
|---|---|
| `_load()` | 读样本 JSON |

| `tasks_in_hour()` | 本小时跑过哪些任务 |
| `energy_by_server()` | 逐服务器能耗、逐任务分摊、空载能耗 |
| `grid_hour()` | 该小时电网结构 |
| `carbon_hour()` | 逐服务器与逐任务碳排 |

### `_overlaps()` 为什么是半开区间

```python
return start < w_to and (end is None or end > w_from)
```

15:30 在跑的任务，绝大多数不是 15:30 开始的。判据必须是**重叠**而非相等：

| 任务起止 | 落在 15:30–15:31 吗 |
|---|---|
| 15:22–15:47 | ✅ 跨越整个窗口 |
| 15:28–**15:31** | ✅ 右端开区间，15:31 结束算命中 |
| 15:20–**15:30** | ❌ 15:30 整结束不算 |
| `ts_end` 为 `None` | ✅ 命中，但这是异常记录，能耗须标 absent |

### `energy_by_server()` 的分摊逻辑

**逐分钟分摊，不是按小时总量分。**

```
某一分钟没有任务在跑  →  这一分钟的电算「空载」（无主）
某一分钟有任务在跑    →  按各任务占用的 GPU 数分摊
```

**空载能耗不摊给任何任务。** 摊了会让任务碳足迹凭空变大，还掩盖了空置问题本身。

守恒关系：`整机能耗 = 空载 + 各任务分摊之和`，测试里误差要求 < 1e-6，实测 < 1e-15。

### `carbon_hour()` 里那个曾经的 bug

它现在调 `core.factor.match()` 取因子，**而不是读样本数据里的 `ef_gco2e_per_kwh`**。

早前两条路径各读各的，恰好都是 280，看不出问题。把因子库改成 999 而不动样本，`query_carbon` 报 2265.5、`energy_flow_report` 报 8083.1——**同一小时两个碳排**。现在全项目只有一个因子入口。

### 基线为什么用中位数，不用空载功率

## `core/storage.py`（83 行）· 储能净碳效果

```python
net_reduction = discharged * (ef_discharge - ef_charge / eta)
```

### 符号约定：正 = 减碳，负 = 增碳

**这里我第二版才改对。** 同一因子加上效率损失，储能**必然增碳**（充进去的比放出来的多），但第一版代码报了"净减碳"——把正负号的含义搞反了。

手算校验：

```
放电 0.4833 kWh，为此需充 0.5492 kWh
抵消 135.3 − 充电排放 153.8 = −18.5 gCO2e  →  净增碳
```

代码里明确写了 `sign_convention` 字段，且**绝不取绝对值、不钳到零**——储能可能增碳正是要算出来的东西。

# 三、闸二：`agent/boundary.py`（66 行）

**全部 Agent 共用这一个出口。** 任何 Agent 不得自带过滤逻辑——多套规则必然出现漏洞。

| 代码 | 含义 |
|---|---|
| `FORBIDDEN` | 直接剔除的字段：IP、序列号、hostname、机房位置、原始路径 |
| `PSEUDONYM` | 脱敏字段：`job_name` → `job-xxxxxx`，`device_id` → `node-xxxxxx` |
| `_GAP_NOTICE` | 有缺口时自动追加的禁令文本 |
| `_scrub()` | 递归剔除与脱敏 |
| `_gap_line()` | 把缺口渲染成一行 |
| `filter_outbound()` | 出网前的唯一出口 |
| `assert_no_leak()` | 兜底自检，可疑即抛异常 |

### 脱敏名单只放身份类字段

`model_id`（Qwen2.5-72B）和 `server_model`（8xH100）曾在名单里，**实跑后移出**——它们是公开型号名而非身份，脱敏之后「哪个模型能耗最高」就没法用人话回答，报告随之失去意义。

### 缺口告知也必须走脱敏

```python
payload = _scrub(env.to_dict())
gaps = payload.get("absent_ranges") or []     # ← 从已脱敏的 payload 拼
```

早前这段是从**未过滤的对象**拼出来的，泄漏了原始设备 ID `srv-03`，还和数据里的 `node-fa0364` 对不上。

### `assert_no_leak()` 的两处教训

```python
for m in re.finditer(r"\b[0-9a-fA-F]{16,}\b", text):
    if any(c in "abcdefABCDEF" for c in m.group(0)):   # ← 必须含字母
        raise ValueError(...)
```

**要求至少含一个字母 a–f。** 实跑时它曾被 `0.39999999999999997` 触发——数字也是合法的十六进制字符，17 位小数尾巴就满足 16 位阈值，正常报告因此被拦下。

代价是纯数字的序列号会漏过，所以真正的防线始终是 `FORBIDDEN` 名单，这条只是兜底。

IPv6 是后来补的——正则原先只覆盖 IPv4，`fe80::…` 写在自由文本里可出网。

# 四、闸三：`agent/verifier.py`（55 行）

**Agent 说出的每个数字，都必须能在工具返回里找到。**

| 代码 | 含义 |
|---|---|
| `_NUM` | 匹配数字，含千分位、小数、**科学计数法** |
| `_TRIVIAL` | 小于 60 的整数 + 100 + 年份，跳过校验 |
| `_ISO_DATE` | 把 ISO 日期拆成年月日 |
| `_numbers()` | 收集 payload 里所有有据的数字 |
| `verify_numbers()` | 逐个核对，容差 1% |

### 科学计数法曾是漏判

`1.2005e3` 只被提取成 `1`（平凡数字）直接放行——编造的数字写成科学计数法可绕过。`_NUM` 已加指数部分 `(?:[eE][+-]?\d+)?`。

### 日期曾是误判

「2026 年 8 月 30 日」被拦：`30` 不在白名单，而 ISO 时间戳 `2026-08-30T15:00:00` 里的 `30` 因后接 `T` 没被正则识别。`_ISO_DATE` 额外拆出年月日解决。

### `_TRIVIAL` 是一个自觉的取舍，不是疏漏

```python
_TRIVIAL = {float(n) for n in range(60)} | {100.0, 2025.0, 2026.0}
```

**小于 60 的整数一律放行。** 报告里必然出现时刻（15:00、45 分钟、30 日），它们与同量级的编造数字无法区分。若严格校验，每份写了日期的正常报告都会被标未通过——**闸三会被用的人直接关掉，那才是真正的失效**。

代价：凭空的「同比下降 15%」可能蒙混过关。可接受，因为本项目真正要守的是能耗与碳排数值，它们几乎总是带小数且远大于 60。

`tests/test_gates.py::test_verifier_blind_spot_is_deliberate` 把这个行为固化成用例——将来有人"修好"它时，测试会提醒这是取舍。

def query_load_profile(hour_start: str) -> str:

# 六、Agent 骨架

## `agent/base.py`（89 行）· 官方 SDK 版

| 代码 | 含义 |
|---|---|
| `MODEL` | `claude-opus-5` |
| `collect_payloads()` | **把证据与错误分开** |
| `system_prompt()` | `_shared.md` + 各自提示词 |
| `run()` | 跑 `tool_runner` → 收返回 → 闸三回检 |

### `collect_payloads()` 解决的是一个隐蔽问题

读 SDK 源码发现：**`tool_runner` 会捕获工具内抛出的任何异常**，用 `repr(exc)` 构造一条带 `is_error` 的普通结果交给模型，循环继续。

两个后果：

1. **闸二靠抛异常阻止泄漏，但异常被咽掉**——运行并不中断，模型只是读到一段错误文本就往下写
2. **错误信息会冒充证据**——异常消息里的数字会成为闸三认可的"来源"

```python
(errors if block.get("is_error") else evidence).append(text)
```

任一工具报错，整份结论标 `verified=False`。

<span style="color:#888">（另确认一处安全：`assert_no_leak` 的异常消息是通用文本、不含被拦下的内容，所以 `repr(exc)` 交给模型不会二次泄漏。）</span>

### `run()` 的调用参数

```python
runner = self.client.beta.messages.tool_runner(
    model=MODEL, max_tokens=max_tokens,
    system=self.system_prompt(),
    thinking={"type": "adaptive"},
    betas=["server-side-fallback-2026-07-01"],
    fallbacks="default",              # 模型拒答时自动降级
    tools=self.tools,
    messages=[{"role": "user", "content": user_input}],
)
```

这些参数经 `inspect.signature` 在 anthropic 1.4.0 上实读确认，不是推测。

## `agent/base_langchain.py`（117 行）· LangChain 版

| 代码 | 含义 |
|---|---|
| `to_langchain_tool()` | **取 `@beta_tool` 对象的 `.func` 原样重包** |
| `_text_of()` | 从块列表里只取 text 块 |
| `as_langchain()` | 由 SDK 版类派生出双胞胎 |

### 为什么三道闸不会因换框架而丢失

```python
return StructuredTool.from_function(
    func=bt.func,        # ← 同一个函数，不是重写的
    ...
)
```

函数是同一个，`_emit()` 就还在调用路径上，**两道闸自动保住**。实测验证过：经 LangChain 包装后调用，设备 ID 照样脱敏、缺口禁令照样附加。

`as_langchain()` 从现有类派生，`name`/`prompt_file`/`tools` 全部继承，**两套实现不可能各自漂移**。

`_text_of()` 是必需的：开启 thinking 后 `AIMessage.content` 是块列表，直接 `str()` 会把 thinking 内容也混进去。

## `agent/snapshot.py`（81 行）· 小时快照

| 代码 | 含义 |
|---|---|
| `SCHEMA` | 主键 `(hour_start, version)` |
| `_normalise_hour()` | **时区归一** |
| `save()` | 追加新版本，**永不覆盖** |
| `load()` / `load_range()` | 取当前版本 / 取一段 |

### 为什么必须追加

数据补采、因子更新、分配方法改了，都要重算。**重算产生新版本，绝不原地覆盖：**

| 场景 | 覆盖式 | 追加式 |
|---|---|---|
| 报告已发给甲方，本周因子更新 | 甲方那份不存在了 | 旧版本仍在 |
| 「这个数当时怎么算的」 | 答不了 | 取 v1 的 `caliber` |

碳核算报告是要对外的，不能复现的报告在审计面前没有价值。

### 时区归一解决的陷阱

`2026-08-30T15:00:00+08:00` 和 `2026-08-30T07:00:00Z` 是**同一时刻**，但字符串排序不同。`load_range` 用字符串比较，不归一就会把一个小时拆成两行。

## `samples/seed_hour.py`（132 行）· 数据生成

**功率不是随机的**，由任务占卡数推出来：

```python
power = idle_kw + (max_kw - idle_kw) * busy_gpus / gpu_count
```

所以能耗与任务内部自洽，重跑结果完全一致。

三个 Agent 的提示词与工具、**工具不得挂在多个 Agent 上**、每个工具都经过边界、LangChain 双胞胎跟得上 SDK 版、查询 Agent 拿不到原始表、失败隔离。

### `_call()` 的写法值得一提

```python
props = tool.input_schema.get("properties", {})
unknown = set(props) - set(SAMPLE_ARGS)
assert not unknown, f"{tool.name} 有测试未覆盖的参数: {unknown}"
```

**按工具自身的 schema 构造参数**，而不是写死 `hour_start`。加 `resolve_time_window(instant=...)` 时旧写法当场失败——这个断言保证新工具不会悄悄绕过边界检查。
