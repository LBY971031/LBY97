# RAG 与 LangChain

这两个词常被拿来比较，但**它们不在同一个维度上**，没法互相替代。这份文档说清楚
它们各自是什么、在本项目里分别用上了哪些、以及**本项目为什么刻意不用向量 RAG**。

最后一条是本文的重点：那不是疏漏，是决定。

---

## 一、一句话区分

| | 它是什么 | 解决什么问题 |
|---|---|---|
| **LangChain** | 一套**框架**（骨架、管道） | 「**怎么调**模型」——怎么让模型能用工具、能多轮循环、能换供应商 |
| **RAG** | 一种**方法**（战术、思路） | 「**喂什么料**」——模型不知道的知识，从外部查出来塞给它 |

<span style="color:#888">（打个比方：LangChain 是厨房——灶台、锅、流水线；RAG 是「照菜谱做菜，不凭记忆瞎做」这条规矩。
厨房里可以守这条规矩，也可以不守；这条规矩在别人家厨房也能守。）</span>

所以正确的说法是：**可以用 LangChain 实现 RAG，也可以不用；LangChain 能做 RAG，
也能只做 Agent 不做 RAG。** 本项目属于后者。

---

## 二、LangChain 在本项目干的四件活

全部集中在 `agent/base_langchain.py` 一个文件里。

| 做什么 | 代码 | 为什么需要它 |
|---|---|---|
| 统一模型接口 | `init_chat_model`（:69） | 换供应商只改一个字符串 |
| 工具封装 | `StructuredTool.from_function`（:38） | 把普通函数变成模型认得的工具，参数说明从 docstring 自动生成 |
| Agent 循环 | `create_react_agent`（:75） | 管「想 → 调工具 → 看结果 → 再想 → 作答」这个循环 |
| 消息与状态 | `ToolMessage` 筛选（:92-96） | 能把出错的工具结果挑出来，不让它进闸三的证据池 |

**第一条最有体感**：Claude 换成 DeepSeek，全项目只改 `.env` 里的 `LC_MODEL`，
Python 代码一行不动。不用 LangChain 的话，Anthropic 与 DeepSeek 是两套完全不同的
SDK，得把整个 Agent 写两遍。

**第三条是核心**。`create_react_agent` 那一行替你省掉的是：自己写 while 循环、
自己解析模型要调哪个工具、自己把工具结果按格式塞回对话历史。

### LangChain 不管的事

这点必须写明，否则容易产生错误的安全感：

> **LangChain 不保证工具算出来的数对不对，也不管模型有没有瞎编。**
> 它只管「话传到了」，不管「话是真是假」。

真话假话是本项目**三道闸**的职责（`agent/contract.py` / `boundary.py` / `verifier.py`），
与用不用 LangChain 完全无关。所以 `agent/base.py`（官方 SDK 版）和
`agent/base_langchain.py`（LangChain 版）两条路的安全性是一样的——因为**它们复用同一批
工具函数**（见 `to_langchain_tool()` 里的 `func=bt.func`）。

## 三、RAG 在 Agent 里是什么形态

**典型 RAG 流程**：文档切块 → 向量化（embedding）→ 存进向量库 → 用户提问时算
相似度、取最相关的 top-k 段 → 塞进提示词 → 模型照着答。

**在 Agent 体系里，RAG 会「退化」成一个可选工具**——模型自己判断要不要调、调几次。
这与传统 RAG「检索一次、生成一次」的固定流程不同：

| | 传统 RAG | Agent 里的检索 |
|---|---|---|
| 谁决定要不要检索 | 流程写死，每次都检索 | **模型自己判断** |
| 检索几次 | 一次 | 想几次就几次 |
| 能不能配合别的工具 | 不能 | 能，检索只是工具之一 |

本项目的 `match_emission_factor`（`agent/subagents/tools_hour.py:166`）正是这个形态：
它躺在 `TOOLS_SUB2` 里，SubAgent 2 自己决定什么时候调。

## 四、本项目为什么不用向量 RAG

**事实先摆出来**：`requirements.txt` 与 `requirements-langchain.txt` 里
**没有任何向量库**——没有 chroma、faiss、pinecone，没有 embedding 相关的包。

但本项目**已经在做 RAG 想解决的那件事**，只是换了实现方式。看 `core/factor.py:24`
的 `match()`：模型**不许凭记忆说「四川电网排放因子是 280」**，必须调工具，由代码
从 `samples/factors.json` 里按明确规则检索，还要把**落选的候选项和它们差多少**
（`delta_vs_selected_pct`，:64）一并返回。

这叫**确定性检索**，不是向量检索。对比如下：

| | 向量 RAG | 本项目的确定性检索 |
|---|---|---|
| 怎么找 | 语义相似度，取 top-k | 明确规则：地理邻近 > 时间粒度 > 年份差（`selection_rule`，:76） |
| **找不到时** | 返回「最相似」的那条——**可能根本不相关，而它不会告诉你** | 返回 `grade: "D"` + `reason`（:48），**明说没有** |
| 可复现 | 取决于 embedding 模型、k 值、库版本 | 同样输入永远同样输出 |
| 能否审计 | 说不清「为什么是这条」 | `selection_rule` 字段写明了规则 |

**「找不到时」这一行是决定性的。**

本项目从头到尾的原则是「**有就是有，没有就是没有，不能交给 LLM，否则会瞎编**」。
向量检索天然违背这条——它的设计就是「总能返回最相似的 k 条」，哪怕全都不相关，
而且**它不具备说「我没找到」的能力**。

对排放因子这种**结构化、数量有限、必须可审计**的数据，向量 RAG 是**错误的工具选择**。
因子库现在只有 5 条，有明确的 `region` / `year` / `scope` 字段，做语义搜索毫无意义。

## 五、什么时候才真的需要向量 RAG

三种情况，**目前都没到**：

1. **从标准文档全文里找规则**——比如「ISO 14067 对共生产品分配是怎么规定的」。
   这是非结构化长文本，规则匹配做不了，向量检索才有用武之地。
2. **文献检索**——`paper/` 目录那类工作。
3. **因子库涨到几万条且带自由文本描述**——那时规则排序会顾不过来。

在那之前引入向量库，只会让「**这个数字是从哪来的**」变得说不清楚——而这恰恰是
本项目最在意的事。

---

## 六、最后一句：RAG 不等于不会幻觉

很多人指望用 RAG 来防幻觉。**RAG 只能降低概率，不能杜绝。** 模型拿到检索结果之后，
照样可能自己做算术、自己换算百分比、自己把两个数加起来。

真正把这条路堵死的是**闸三**（`agent/verifier.py`）：

> 输出里**每一个数字**都必须能在工具返回值里找到原文，找不到就 `verified=False`。

这是一道**事后校验**，与模型用了什么检索方式无关，也与用不用 LangChain 无关。
换模型之后闸三可能报警更频繁（不同模型遵守「不得自行做算术」的程度不同），
这不是 bug，正是它该有的反应——详见 [快速开始](./快速开始.md) 的「换用 DeepSeek」一节。

---

## 小结

| | 本项目用了吗 | 在哪 |
|---|---|---|
| LangChain | 用了，作为**可选层** | `agent/base_langchain.py`；默认走 `agent/base.py` 也能跑 |
| 向量 RAG | **没用，也暂时不需要** | — |
| 检索这件事本身 | 用了，确定性版本 | `core/factor.py` 的 `match()` |
| 防瞎编 | 靠三道闸，**不靠 RAG** | `contract.py` / `boundary.py` / `verifier.py` |
