# 三个分配问题能否靠 Skill 解决？

> 编制日期：2026-09-07
> 起因：[对标审计](./成熟工作流对标审计.md) P0-1 指出分配规则缺失，本文回答「能否在 SubAgent 中部署 Skill 来解决」
> **结论先行：能解决一部分，但三个问题里 Skill 的占比差别极大，且第一个问题的瓶颈根本不在 Skill。**

---

## 一、先建一个判断框架

要回答「Skill 能不能解决」，先得分清一件事卡在哪一层：

| 层 | 管什么 | 谁来做 | Skill 有用吗 |
|---|---|---|---|
| **① 采集层** | 硬件/驱动**能不能测到**这个量 | `collectors/` + 硬件能力 | ❌ **完全无用**——测不到就是测不到 |
| **② 计算层** | 测到之后**怎么算**分摊 | `core/allocation.py` 确定性算法 | ❌ **不该用**——数字必须算死，不能交给 LLM |
| **③ 判断层** | 该用哪条规则、假设怎么声明、局限怎么写 | **Skill** | ✅ **这才是 Skill 的地盘** |

> 这个分层直接来自 [能碳.md §8.2](../能碳.md#82-主-agent编排层) 的原则：**数字由代码算，话由 Agent 说。**
> Skill 属于"话"的部分——它决定 Agent **怎么判断、怎么声明**，不决定数字本身。

---

## 二、逐个问题拆解

### 问题一 · 一台 8 卡机同时跑 3 个任务，整机功耗怎么分？

#### 瓶颈在采集层，不在 Skill

⚠️ **重要更正**：[对标审计](./成熟工作流对标审计.md) P0-1 中我写「分卡计量技术上可行，应作为首选」——**这个说法过于乐观**。检索显示存在系统性测量局限：

| 局限 | 内容 |
|---|---|
| **采样覆盖不足** | `nvidia-smi` 在 A100/H100 上**仅对约 25% 的运行时段采样功率**，未采样期间 GPU 功耗可能截然不同，可导致能耗**严重高估或低估** |
| **MIG 分区无硬件支持** | 多实例 GPU 的**分区级功耗归属缺乏硬件支持**，准确分摊困难，需借助基于分区级利用率指标的 ML 功耗模型估算 |
| **进程级归属不可复现** | 部分 NVIDIA 硬件上，进程级能耗归属**无法通过受支持接口复现**，仅有 NVML 瞬时功率可用 |

> 📎 依据来自检索摘要（arXiv 2312.02741「nvidia-smi's Lack of Attention」、2501.17752「On the Partitioning of GPU Power among Multi-Instances」、2605.27599「The Energy Blind Spot」、2307.05647「EnergAt」）。
> **均为预印本，需自行核实是否已发表及具体实验条件。**

#### 一个可用的工程手段

检索提到：**用整机实测总功耗去缩放分区功耗预测，可以消除总量误差并降低单分区误差**。

映射到你的场景，就是一条**"分摊结果必须回加等于实测总量"**的约束：

```
Σ(各任务分摊能耗) ≡ 整机实测能耗      ← 硬约束，差额不允许被丢弃

若逐卡读数之和 ≠ 整机实测：
  按逐卡读数的相对比例，把差额按比例回摊
  并记录 residual_pct（差额占比）作为数据质量指标
```

#### 三层归属

| 层 | 该做什么 | 占比 |
|---|---|---|
| ① 采集 | 逐卡功率 + **整机总功耗**（两者都要，后者用于校准） | **主要瓶颈** |
| ② 计算 | 归一化回加约束、按卡时/显存份额兜底分摊 | 主体工作 |
| ③ Skill | 判定当前具备哪一级分配条件、**声明测量局限**、`residual_pct` 超阈值时提示不可靠 | **约 20%** |

> **结论**：Skill 在这个问题上的作用**不是指导怎么分摊**，而是**逼 Agent 老实交代测量局限**。
> 这仍然有价值——但如果你以为装个 skill 就能把功耗分准，那是误解。

### 问题二 · 共享网络/存储/制冷怎么摊到各模型？

#### 瓶颈在"选哪个分摊基准"——这是判断题

制冷相对好办（按 IT 电耗比例摊，这正是 PUE 的隐含逻辑）。**难的是网络与存储**：

| 候选基准 | 适合什么 | 问题 |
|---|---|---|
| 按卡时 | 计算密集型任务 | 对 IO 密集型任务不公平 |
| 按流量 | 网络分摊 | 需要按任务的流量计量，多数环境没有 |
| 按存储占用量×时长 | 存储分摊 | 冷热数据差异大 |
| 按算力份额 | 通用 | 与实际资源占用可能脱节 |

**没有唯一正确答案**——这正是 ISO 分配层级里"物理分配"的典型情形，**需要判断 + 透明声明**。

#### 三层归属

| 层 | 该做什么 | 占比 |
|---|---|---|
| ① 采集 | 分项计量（网络/存储/制冷分开的电表或估算） | 中等瓶颈 |
| ② 计算 | 按选定基准执行分摊 | 简单 |
| ③ Skill | **给出基准选择规则与理由**、要求做基准敏感性分析、强制声明 | **约 40%** |

> **结论**：Skill 在这里有实质作用——它把「随便选个基准」变成「有依据地选，并说明换个基准结果会差多少」。

### 问题三 · 训练碳怎么摊到推理 Token？

#### 瓶颈在判断层——Skill 的主场

**好消息：业界已有命名框架，你不用自创。** 检索显示存在明确的边界分层：

| 边界 | 含什么 |
|---|---|
| **Boundary B** | 分配给用户算力份额的**硬件隐含碳** |
| **Boundary C** | 在 B 之上，再加**上游训练排放按 Token 的分配** |

> ⭐ **这正是你缺的那一层**。你现在的「每百万 Token 碳足迹」大致处在 B，**要补的就是升到 C**。
> 采用 B/C 术语的好处：可对标、审稿人认、不用解释自造概念。

**标准摊销做法**（检索所述）：硬件制造碳按寿命摊到每 GPU 小时，再乘以使用的 GPU 小时数。
一个被引用的假设示例是 4 年 GPU 寿命对应约 **0.013 kgCO₂eq / GPU·h**——**这是某项研究的假设值，不是通用常数，务必按你的设备核算。**

**一个关键量级参考**：检索提到 GPT-4 训练约用 13 万亿 token，而**约 121 天的推理服务排放即可与其训练排放相当**。

这个数字对你的方法有直接含义：

> **模型服务量越大，训练碳摊到每 Token 上就越薄。**
> 所以「每百万 Token 碳足迹」这个指标**对服务量高度敏感**：
> - 长期高负载服务的模型 → 训练碳几乎可忽略
> - **服务量小或刚上线的模型 → 训练碳可能是大头**
>
> 这意味着你**必须把"预期总服务量"作为显式假设声明，并做敏感性分析**。
> 这条本身就可以成为论文里一个有价值的讨论点。

#### 三层归属

| 层 | 该做什么 | 占比 |
|---|---|---|
| ① 采集 | 训练任务的卡时与能耗、模型的累计/预期服务 Token 量 | 可获得 |
| ② 计算 | 摊销公式执行、敏感性区间计算 | 简单 |
| ③ Skill | **边界 B/C 的选择与声明、摊销规则选项、预期服务量假设的表述、敏感性分析要求** | **约 65%** |

> **结论**：这个问题**最适合用 Skill 解决**。因为难点不在测量也不在计算，而在**方法学选择与假设透明化**。

## 三、汇总：Skill 能解决多少

| 问题 | 主要瓶颈 | Skill 占比 | Skill 的实际作用 |
|---|---|---|---|
| **一 · 整机功耗分到任务** | **采集层**（硬件测量局限） | ~20% | 声明测量局限、判定可用分配级别、残差超限时告警 |
| **二 · 共享设施分摊** | **计算层**（基准选择） | ~40% | 给基准选择规则、强制敏感性分析 |
| **三 · 训练碳摊到 Token** | **判断层**（方法学） | **~65%** | **边界 B/C 选择、假设声明、敏感性要求** |

**一句话回答你的问题**：

> **可以部署，但不要指望 Skill 把这三个问题都解决掉。**
> 问题三基本可以靠 Skill 解决；问题二 Skill 能解决一半；
> **问题一的瓶颈在硬件测量，Skill 只能让 Agent 诚实地承认测不准，不能让它变准。**

## 四、建议新增的三个 Skill

### S1-4 `allocation-hierarchy` · 分配层级判定 【装在 SubAgent 1】

**何时使用**：任何需要把共享资源能耗归到具体任务/模型时。

**核心内容**：

1. **判定当前具备哪一级分配条件**
   ```
   有可靠逐卡计量 + 整机总功耗校准 → 层级①细分
   仅有整机功耗 + 卡时/显存数据     → 层级②物理分配
   仅有计费数据                     → 层级③经济分配（最后手段）
   ```
2. **回加约束**：`Σ分摊 ≡ 实测总量`，残差按比例回摊并记录 `residual_pct`
3. **测量局限声明清单**（硬性）：
   - 采样覆盖不足（A100/H100 的 25% 采样问题）
   - MIG 分区无硬件级功耗归属
   - `residual_pct` 超阈值（建议 5%）时标注"分摊结果不可靠"
4. **禁止**：不许在没有说明局限的情况下给出精确到小数点后多位的分摊结果

---

### S2-5 `shared-infra-allocation` · 共享设施分摊基准 【装在 SubAgent 2 或 1】

**核心内容**：

1. 制冷：按 IT 电耗比例分摊（与 PUE 逻辑一致）
2. 网络/存储：给出候选基准表与各自适用条件（见上文表格）
3. **强制敏感性分析**：至少给出两种基准下的结果差异
4. **禁止**：不许静默选定一个基准

---

### S3-4 `boundary-and-amortization` · 边界分层与训练碳摊销 【装在 SubAgent 3，优先级最高】

**核心内容**：

1. **边界声明**：明确本次核算处于 Boundary B 还是 C，**结果必须带边界标记**
2. **训练碳摊销公式与假设**
   ```
   每Token训练碳分摊 = 训练总碳 ÷ 预期总服务Token量
                       ↑ 这是估计值，必须作为显式假设声明
   ```
3. **强制敏感性分析**：预期服务量取 0.5×、1×、2× 时结果如何变化
4. **量级提示**：服务量大时训练碳被摊薄，服务量小或新上线模型时占比可能很大
5. **禁止**：不许在未声明预期服务量假设的情况下报出含训练碳的数字

## 五、必须靠代码的部分（Skill 替代不了）

| 模块 | 干什么 | 为什么不能交给 Skill |
|---|---|---|
| `collectors/gpu_collector.py` | 逐卡功率 + **整机总功耗**双采集 | 采集不到，方法论无用武之地 |
| `core/allocation.py` | 三级分摊算法、回加约束、残差计算 | **数字必须确定可复现**，不能有 LLM 随机性 |
| `core/amortization.py` | 训练碳摊销与敏感性区间 | 同上 |

**数据模型同步**（在[审计](./成熟工作流对标审计.md)已列字段基础上再加）：

| 表 | 新增字段 | 用途 |
|---|---|---|
| `energy_records` | `residual_pct` | 分摊残差占比，数据质量指标 |
| `carbon_records` | `allocation_method` | 用了哪一级分配 |
| `carbon_records` | `boundary_level` | **B 或 C** |
| `carbon_records` | `expected_service_tokens` | 摊销假设的预期服务量 |
